## ADDED Requirements

### Requirement: Postgres is the sole persistence engine

The system SHALL use Postgres for all durable application state. Notion MUST NOT be read from or written to by any runtime code. The `@notionhq/client` dependency MUST be absent from every `package.json` in the workspace after this change.

#### Scenario: Grep for notion imports is empty
- **WHEN** a developer greps the codebase for `@notionhq/client` or `notion-client`
- **THEN** no runtime file matches (only historical docs or changelog entries may reference Notion)

#### Scenario: App boots without Notion env vars
- **WHEN** the API is started with none of `NOTION_API_KEY`, `NOTION_KNOWLEDGE_PAGE_ID`, `NOTION_OUTPUT_PAGE_ID`, or `NOTION_SCHEDULES_DATABASE_ID` defined
- **THEN** the app boots successfully as long as `DATABASE_URL` is valid

### Requirement: MikroORM is the data-access layer

The workspace SHALL use MikroORM (`@mikro-orm/core` + `@mikro-orm/postgresql`) for entity modeling, migrations, and queries. Entities MUST live in `packages/db/src/entities/` and be declared with MikroORM decorators. Raw SQL MAY be used only for complex reports where the ORM adds no value, and MUST be isolated in repository methods.

#### Scenario: Every table has a MikroORM entity
- **WHEN** a developer inspects `packages/db/src/entities/`
- **THEN** there is exactly one entity class per table, and every entity is registered in the MikroORM config's `entities` array

#### Scenario: NestJS module uses @mikro-orm/nestjs
- **WHEN** the API bootstraps
- **THEN** it imports `MikroOrmModule.forRoot()` with config from `packages/db`, and feature modules import `MikroOrmModule.forFeature([...])` for their entities

### Requirement: Connection configuration

The Postgres connection SHALL be configured from a single `DATABASE_URL` environment variable. The app MUST fail to start if `DATABASE_URL` is unset or if the database is unreachable at startup. Connection pooling defaults MUST be sane for a single API process (pool min 2, max 10).

#### Scenario: Missing DATABASE_URL aborts startup
- **WHEN** the API is started without `DATABASE_URL`
- **THEN** startup exits non-zero with an error message identifying the missing variable

#### Scenario: Unreachable database aborts startup
- **WHEN** `DATABASE_URL` is set but points to a host that refuses the connection
- **THEN** startup exits non-zero after the ORM's connection attempt, with the underlying error included in the log

### Requirement: Schema migrations

The database schema SHALL be versioned via MikroORM migrations stored in `packages/db/src/migrations/`. Applying schema changes MUST go through `mikro-orm migration:create` and MUST NOT rely on `schemaGenerator.updateSchema()` at runtime. The app MUST NOT auto-sync entities to the database on boot.

#### Scenario: First-time setup runs migrations
- **WHEN** a developer runs `turbo run db:migrate` against an empty database
- **THEN** all migrations apply in order and the schema matches the current entity definitions

#### Scenario: Boot does not auto-sync
- **WHEN** the API starts
- **THEN** no `ALTER TABLE` or `CREATE TABLE` is issued by the app process

### Requirement: Local dev has a Postgres container

The repo SHALL ship a `docker-compose.yml` defining a `postgres` service suitable for local development (Postgres 16, a mounted volume for persistence, port 5432 exposed to localhost). `CLAUDE.md` and `README.md` MUST document `docker-compose up -d postgres` as the prerequisite for `turbo run dev`.

#### Scenario: Fresh clone → working database
- **WHEN** a developer clones the repo, runs `docker-compose up -d postgres`, sets `DATABASE_URL`, and runs `turbo run db:migrate`
- **THEN** the schema exists and `turbo run dev` succeeds

### Requirement: Repository interface stability

Repositories in `packages/db/src/repositories/` SHALL expose the same public method names that the former Notion repositories exposed, so that `BaseAgent` tool implementations are edited only for imports, not for logic. Example: `ProductsRepository.getProduct(name)`, `LeadsRepository.saveLead(lead)`, `FeedbackRepository.saveFeedback(entry)`.

#### Scenario: Agent code diff is minimal
- **WHEN** an agent's tool implementation that previously called the Notion `LeadsRepository.saveLead(...)` is updated
- **THEN** the change is limited to the import path; the method name and argument shape are identical

### Requirement: No Notion residue in domain types

Shared domain types in `packages/types` MUST NOT reference `notionPageId`, `notionDatabaseId`, or any other Notion-specific field. Entity primary keys SHALL be UUIDs generated by Postgres.

#### Scenario: Lead type has no notionPageId
- **WHEN** a consumer imports `Lead` from `@hothotleads/types`
- **THEN** the type has an `id: string` (UUID) and no `notionPageId` field
